## 情報源タイプ

**型**: Select（単一選択）
**必須**: ✅
**プロパティ詳細**: [property-definitions.md](./property-definitions.md#3-情報源タイプ)

### 候補値

| 値 | カラー | 定義 | 主な使用シーン |
|---|---|---|---|
| `interview` | Blue | 構造化インタビュー | JTBDインタビュー、UXリサーチ |
| `survey` | Green | アンケート | NPS、満足度調査 |
| `sales_call` | Orange | 営業電話・商談 | 商談メモ、訪問記録 |
| `support` | Red | サポート問い合わせ | 問い合わせログ、Q&A |
| `sns` | Pink | SNS投稿 | Twitter、LinkedIn、口コミサイト |
| `review` | Yellow | レビュー記事・口コミ | 業界誌、レビューサイト |
| `analytics` | Purple | 行動データ | アクセス解析、利用ログ |

### 判定ルール
- 1件のinsightにつき1つ選択
- 複数情報源の合成は禁止（別エントリとして登録）
- 該当しない場合は最も近いものを選択

### 判定例

| 状況 | 選択値 |
|---|---|
| 顧客に1時間ヒアリング | `interview` |
| Webアンケートの自由記述 | `survey` |
| 営業同行時のメモ | `sales_call` |
| サポートチケットの内容 | `support` |
| Twitter投稿の引用 | `sns` |
| 業界誌のインタビュー記事 | `review` |
| Google Analyticsの行動分析 | `analytics` |

## 顧客属性

**型**: Select（単一選択）
**必須**: ✅
**プロパティ詳細**: [property-definitions.md](./property-definitions.md#5-顧客属性)

### 候補値

| 値 | カラー | 定義 | 判定基準 |
|---|---|---|---|
| `意思決定者` | Red | 最終決裁権を持つ者 | 予算・契約の最終承認権限 |
| `決裁関与者` | Orange | 決裁プロセスに影響を与える者 | 役員、部長、顧問 |
| `実務担当者` | Yellow | 業務遂行を担う者 | 日常業務でツールを使う担当者 |
| `利用者` | Green | サービス・製品の実際の使い手 | エンドユーザー |
| `導入推進者` | Blue | 導入を主導する者 | プロジェクトマネージャー、推進役 |
| `既存顧客` | Purple | 既に契約・利用中の顧客 | 契約済み |
| `見込み顧客` | Pink | 未契約だが購買検討段階の対象 | 商談中、検討中 |
| `代理店・パートナー` | Brown | 販売・導入支援を行う第三者 | 販売代理店、SIer |
| `不明` | Gray | 判定材料が不足 | デフォルト |

### 設計思想

- 役職ではなく**購買・利用プロセス上の役割**で分類
- JTBD分析では肩書きより「どの立場でそのjobを抱えているか」が重要
- 役職を管理したい場合は `役職・立場` `所属部門` プロパティを併用

### 判定例

| 状況 | 選択値 |
|---|---|
| 中小企業代表が決裁する | `意思決定者` |
| 部長が決裁前に意見する | `決裁関与者` |
| 経理担当が日々ツールを使う | `実務担当者` |
| 一般従業員がエンドユーザー | `利用者` |
| 情シス担当が導入を主導 | `導入推進者` |
| 既存契約のクライアント | `既存顧客` |
| 商談中のリード | `見込み顧客` |
| 販売代理店の営業 | `代理店・パートナー` |

### 重複時の優先順位

複数該当する場合の優先順位：

1. `意思決定者` > `決裁関与者` > `導入推進者` > `実務担当者` > `利用者`
2. `既存顧客` `見込み顧客` `代理店・パートナー` は別軸（上記と重複可だが本DBでは1つ選択）
3. 判定不能時は `不明`

### 見直しトリガー
- 20〜30件累積時点で分類の妥当性を再評価
- 業界・規模で偏りがある場合は分類軸の追加を検討

## Forces

**型**: Multi-select（複数選択可）
**必須**: ✅（条件付き。詳細は [property-definitions.md §8](./property-definitions.md#8-forces)）
**プロパティ詳細**: [property-definitions.md](./property-definitions.md#8-forces)

### 候補値

| 値 | カラー | 定義 |
|---|---|---|
| `Push` | Red | 現状から押し出す力（不満・問題・痛み・現状への怒り） |
| `Pull` | Green | 新しい解決策へ引き寄せる力（期待・得たい結果・理想像） |
| `Anxiety` | Orange | 変化への不安・懸念（失敗の恐れ・リスク・社内反発） |
| `Habit` | Gray | 現状維持を促す力（慣性・習慣・既存業務との癒着） |

### JTBD理論的背景

JTBDの「Forces of Progress」モデル：

```
   Push（現状から押す）        Pull（新解決策が引く）
        ↓                           ↑
   ┌──────────────────────────────────┐
   │  顧客の意思決定                   │
   └──────────────────────────────────┘
        ↑                           ↓
   Habit（現状を維持）         Anxiety（変化を妨げる）
```

- `Push` + `Pull` = 変化を促す力
- `Habit` + `Anxiety` = 変化を妨げる力
- 両者の力関係で顧客行動が決定される

### 判定例

| 生の声の内容 | Forces |
|---|---|
| 「今のシステムが遅くて業務にならない」 | `Push` |
| 「自動化で月20時間削減したい」 | `Pull` |
| 「導入失敗したら社内で責められる」 | `Anxiety` |
| 「20年これでやってきた」 | `Habit` |
| 「遅くて困ってる、でも変えるのは怖い」 | `Push`, `Anxiety` |
| 「効率化したいが、慣れたやり方を捨てるのは抵抗ある」 | `Pull`, `Habit` |

### 判定ルール
- 生の声に**明示的に該当する内容**がある場合のみ選択
- 推測で選ばない
- **空欄可**（ただし `レビュー状態 = 確定` 時は、最低 1 つ選択 **または** `要約` の【主訴】に空欄理由を明記）
- 複数該当する場合は複数選択

### 空欄可と必須の関係

`Forces` は **条件付き必須** プロパティである（Notion の UI 必須とは別概念）。

- AI autofill 直後の空欄: 許容（該当なしが正しい場合がある）
- レビュー中の空欄: 許容（妥当性はレビュアーが判定）
- `レビュー状態 = 確定` 時: **最低 1 つ選択** か **空欄理由を要約に明記** のどちらかが必要

詳細: [property-definitions.md §8 Forces](./property-definitions.md#8-forces)

### VPC接続マッピング

| Forces | VPC接続先 |
|---|---|
| `Push` | VPC.Pains |
| `Pull` | VPC.Gains |
| `Anxiety` | VPC.Pains（心理的痛み） |
| `Habit` | job.現状代替手段 |

## ジャーニー段階

**型**: Select（単一選択）
**必須**: ✅
**プロパティ詳細**: [property-definitions.md](./property-definitions.md#9-ジャーニー段階)

### 候補値

| 値 | カラー | 定義 | 主な指標 |
|---|---|---|---|
| `認知` | Gray | 課題や選択肢をまだ広く知り始めた段階 | 「最近知った」「聞いたことがある」 |
| `興味` | Blue | 課題意識があり、関連情報に関心を持ち始めた段階 | 「調べている」「関心がある」 |
| `比較` | Yellow | 複数案や複数サービスを見比べている段階 | 「A社とB社で迷っている」 |
| `検討` | Orange | 導入候補が絞られ、具体条件を詰めている段階 | 「予算」「契約条件」「導入時期」 |
| `導入` | Green | 契約・実装・利用開始に関する段階 | 「契約した」「実装中」「初期設定」 |
| `継続` | Purple | 利用後の定着・改善・更新・活用拡大の段階 | 「3ヶ月使った」「現場に広がってきた」 |
| `離脱・見送り` | Red | 導入しない・解約する・保留する理由が中心の段階 | 「やめた」「保留」「他社にした」 |
| `不明` | Default | 判定材料が不足している場合 | デフォルト |

### 判定優先順位

1. **生の声に明示された段階情報を優先**
2. 明示されない場合のみ Forces やジャーニー文脈から推定
3. 推定根拠が薄い場合は `不明`

### 判定例

| 生の声の内容 | ジャーニー段階 |
|---|---|
| 「最近こういうサービスがあるって聞いた」 | `認知` |
| 「もっと詳しく知りたい、資料請求した」 | `興味` |
| 「A社、B社、C社を比較中」 | `比較` |
| 「価格と機能のバランスを詰めている」 | `検討` |
| 「先月契約した、実装中」 | `導入` |
| 「導入3ヶ月、現場で活用が広がってきた」 | `継続` |
| 「他社に決めた」「保留することにした」 | `離脱・見送り` |
| 「困っている、対策を考えたい」（段階不明） | `不明` |

### BMC接続

`顧客属性` × `ジャーニー段階` の組み合わせで Customer Segments を構成：

```
意思決定者 × 検討 → セグメントA
実務担当者 × 継続 → セグメントB
見込み顧客 × 比較 → セグメントC
```

## レビュー状態

**型**: Select（単一選択）
**必須**: ✅
**デフォルト値**: `下書き`
**プロパティ詳細**: [property-definitions.md](./property-definitions.md#15-レビュー状態)

### 候補値

| 値 | カラー | 定義 | 戦略立案使用 |
|---|---|---|---|
| `下書き` | Gray | AI autofill完了、レビュー未着手 | ❌ |
| `レビュー中` | Yellow | レビュー実施中 | ❌ |
| `確定` | Green | レビュー完了、戦略立案に使用可 | ✅ |

### 状態遷移ルール

```
[新規作成]
    ↓
[下書き] ─── レビュー開始 ──→ [レビュー中]
                                    │
                                    ├── 修正必要 ──→ [下書き]
                                    │
                                    └── 承認 ──→ [確定]
                                                     │
                                                     └── 重大な問題発見 ──→ [レビュー中]
```

### 状態別の運用ルール

#### `下書き`
- AI autofill 直後の状態
- 編集可能
- 集計・戦略立案から除外
- レビュー開始前にここに留める

#### `レビュー中`
- レビュアーが確認中の状態
- レビュアー以外の編集を控える
- ハルシネーション検出・修正を実施

#### `確定`
- レビュー完了後の状態
- `レビュー者` `レビュー日` の記入が必須
- 戦略立案・VPC/BMC連携の対象
- 確定後の編集には新規エントリ作成を推奨

### Human-in-the-Point 原則
- AI autofill 結果のみで `確定` にすることを禁止
- 必ず人手レビューを経る
- 詳細: [docs/governance/human-in-the-point.md](../docs/governance/human-in-the-point.md)

## 全体的な運用ルール

### Select 候補値の追加・変更ルール

1. **追加判断**:
   - 既存候補で表現できない明確な役割・段階が頻出する場合
   - 20〜30件以上の累積データで判定不能ケースが20%超える場合

2. **追加プロセス**:
   - 仮運用期間（1ヶ月）を設ける
   - 既存データへの影響を検証
   - SPECIFICATION.md / property-definitions.md / select-options.md を同期更新

3. **削除判断**:
   - 6ヶ月以上使用されていない候補
   - 他候補と統合可能な候補

4. **削除プロセス**:
   - まず非推奨フラグを立てる
   - 既存使用箇所を別候補に移行
   - 完全削除は3ヶ月の移行期間後

### カラー設定の考え方

- 関連性のある候補は近い色相
- 重要度の高い候補は鮮やかな色
- `不明` `下書き` 等のデフォルト系は Gray
- 危険・離脱系は Red 系
- 完了・成功系は Green 系
