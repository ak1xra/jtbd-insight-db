## 顧客属性（Select候補）

| 値 | 定義 |
|---|---|
| `意思決定者` | 最終決裁権を持つ者 |
| `決裁関与者` | 決裁プロセスに影響を与える者 |
| `実務担当者` | 業務遂行を担う者 |
| `利用者` | サービス・製品の実際の使い手 |
| `導入推進者` | 導入を主導する者 |
| `既存顧客` | 既に契約・利用中の顧客 |
| `見込み顧客` | 未契約だが購買検討段階の対象 |
| `代理店・パートナー` | 販売・導入支援を行う第三者 |
| `不明` | 判定材料が不足 |

**運用ルール:**
- `比較検討者` は v1.3 から削除（`ジャーニー段階` の `比較` `検討` と重複のため）
- 役職・部門は別プロパティで管理
- 20〜30件たまったら見直す

## Forces of Progress（Multi-select候補）

JTBDの「Forces of Progress」フレームに準拠。1件のinsightは複数のForcesを同時に含むため Multi-select。

| 値 | 定義 | 例 |
|---|---|---|
| `Push` | 現状から押し出す力（不満・問題・痛み） | 「今のシステムが遅すぎて業務にならない」 |
| `Pull` | 新しい解決策へ引き寄せる力（期待・望ましい結果） | 「自動化で残業を月20時間減らしたい」 |
| `Anxiety` | 変化への不安・懸念 | 「導入失敗したら社内で責められる」 |
| `Habit` | 現状維持を促す力（慣性・習慣） | 「今のやり方で20年回してきた」 |

## ジャーニー段階（Select候補）

| 値 | 定義 |
|---|---|
| `認知` | 課題や選択肢をまだ広く知り始めた段階 |
| `興味` | 課題意識があり、関連情報に関心を持ち始めた段階 |
| `比較` | 複数案や複数サービスを見比べている段階 |
| `検討` | 導入候補が絞られ、具体条件を詰めている段階 |
| `導入` | 契約・実装・利用開始に関する段階 |
| `継続` | 利用後の定着・改善・更新・活用拡大の段階 |
| `離脱・見送り` | 導入しない・解約する・保留する理由が中心の段階 |
| `不明` | 判断材料が不足している場合 |

## AI autofill 用プロンプト

### 共通方針
- モデル: **Notion AI Opus 4.6**
- 一次情報は `生の声` のみ
- `生の声` に明示されていない情報は推測しない（ハルシネーション抑止）
- 出力フォーマット厳守

---

### 1. `insight名` autofill プロンプト

```text id="title_ai_prompt_v2"
以下の insight 情報から、25文字以内の見出しを作成してください。

入力:
- 生の声: {{生の声}}
- 顧客属性: {{顧客属性}}

出力ルール:
- 25文字以内
- 体言止め
- 顧客の主訴または核心を一文で表現
- 説明・装飾語不要
- 候補は1つのみ

出力形式: 見出しテキストのみ
```

---

### 2. `Forces` autofill プロンプト

```text id="forces_ai_prompt_v2"
以下の insight 情報を読み、該当する Forces of Progress を選んでください。
複数該当する場合は複数選択可。

候補:
- Push: 現状から押し出す力（不満・問題・痛み・現状への怒り）
- Pull: 新しい解決策へ引き寄せる力（期待・得たい結果・理想像）
- Anxiety: 変化への不安・懸念（失敗の恐れ・リスク・社内反発）
- Habit: 現状維持を促す力(慣性・習慣・既存業務との癒着)

判定ルール:
- 「生の声」に明示的に該当する内容がある場合のみ選択する
- 推測で選ばない
- 該当なしの場合は何も選ばない（空欄）

入力:
- 生の声: {{生の声}}
- 情報源タイプ: {{情報源タイプ}}
- 顧客属性: {{顧客属性}}

Few-shot example:

例1:
生の声: 「今の会計ソフトが遅すぎて月次が締まらない。クラウドに変えたいが、データ移行で失敗するのが怖い」
出力: Push, Pull, Anxiety

例2:
生の声: 「20年これで回してきたから、変える理由がない」
出力: Habit

例3:
生の声: 「来期から法改正で対応必須」
出力: Push

出力形式: カンマ区切り、候補の英語ラベルのみ（例: Push, Anxiety）
説明文は不要
```

---

### 3. `ジャーニー段階` autofill プロンプト

```text id="journey_ai_prompt_v2"
以下の insight 情報を読み、顧客の購買・意思決定プロセス上の段階を 1つだけ選んでください。

候補と判定ルール:
- 認知: 課題や選択肢をまだ広く知り始めた段階
- 興味: 課題意識があり、関連情報に関心を持ち始めた段階
- 比較: 複数案や複数サービスを見比べている段階
- 検討: 導入候補が絞られ、具体条件を詰めている段階
- 導入: 契約、実装、利用開始の段階
- 継続: 利用後の定着、改善、更新、活用拡大の段階
- 離脱・見送り: 導入しない、解約する、保留する理由が中心の段階
- 不明: 判定材料が不足している場合

判定優先順位:
1. 生の声に明示された段階情報を優先
2. 明示されない場合のみ Forces やジャーニー文脈から推定
3. 推定根拠が薄い場合は「不明」

入力:
- 生の声: {{生の声}}
- 情報源タイプ: {{情報源タイプ}}
- 顧客属性: {{顧客属性}}

Few-shot example:

例1:
生の声: 「他社のA社、B社、C社と比べて、価格と機能のバランスを見ています」
出力: 比較

例2:
生の声: 「導入してから3ヶ月、現場の活用が広がってきた」
出力: 継続

例3:
生の声: 「最近こういうサービスがあるって聞いた程度」
出力: 認知

出力形式: 候補のうち1語のみ（日本語ラベル）
説明文は不要
```

### 4. `要約` autofill プロンプト（Forces構造化要約）

```text id="summary_ai_prompt_v2"
以下の insight 情報を、Forces of Progress フレームに沿った構造化要約に変換してください。

入力:
- 生の声: {{生の声}}
- 顧客属性: {{顧客属性}}
- ジャーニー段階: {{ジャーニー段階}}

出力フォーマット（厳守）:

```
【主訴】（1文・25文字以内）

【Push】生の声から読み取れる不満・問題（明示なしの場合は「該当なし」）
【Pull】生の声から読み取れる望む結果・期待（明示なしの場合は「該当なし」）
【Anxiety】生の声から読み取れる不安・懸念（明示なしの場合は「該当なし」）
【Habit】生の声から読み取れる現状維持要因（明示なしの場合は「該当なし」）

【選定基準・見送り理由】生の声に明示されている場合のみ記載（なければ「該当なし」）
```

判定ルール:
- 「生の声」に明示されていない情報は記載しない
- 推測・補完・拡張は禁止
- 各項目は1〜2文以内
- 「該当なし」を恐れず使う

Few-shot example:

入力:
生の声: 「今のExcel管理が限界。クラウド化したいが、ITに弱い高齢スタッフがついてこれるか心配。月3万までなら出せる」
顧客属性: 意思決定者
ジャーニー段階: 検討

出力:
【主訴】Excel管理の限界とクラウド化検討

【Push】Excel管理が業務量に対して限界に達している
【Pull】クラウド化による業務効率化を望む
【Anxiety】高齢スタッフの操作習熟に不安
【Habit】該当なし

【選定基準・見送り理由】月額予算3万円以内
```

## VPC / BMC 接続設計

採用案A の Forces ラベル化により、後段の VPC / BMC への変換が機械的に可能になる。

### Forces → VPC マッピング

| Forces | VPC要素 | 接続先プロパティ案 |
|---|---|---|
| Push | Pains | VPC DBの `Pains` プロパティ |
| Pull | Gains | VPC DBの `Gains` プロパティ |
| Anxiety | Pains（心理的） | VPC DBの `Pains` プロパティ |
| Habit | Customer Jobs（現状の代替手段） | job DBの `現状代替手段` プロパティ |

### BMC接続

- `顧客属性` × `ジャーニー段階` の組み合わせ → BMCの Customer Segments
- `重要度` 4以上 + `確からしさ` 4以上 のinsightのみ → 戦略意思決定の根拠データとして採用

## 運用ルール（v2.0）

### 入力フロー（`SPECIFICATION.md` §7.1 準拠）

1. 一次情報を `生の声` に貼り付ける
2. `情報源タイプ` `取得日` `顧客属性` を設定する（任意: `役職・立場` `所属部門`）
3. AI autofill を実行する: `insight名` → `Forces` → `ジャーニー段階` → `要約`
4. `重要度` `確からしさ` を人手で設定する（AI に任せない）
5. `job` `タグ` を Relation で接続する（`レビュー状態 = 下書き` の前に `job` は必須）
6. `レビュー状態 = 下書き` とし、その後のレビューで `Forces` `ジャーニー段階` `要約` を人が確認する
7. 必要なら修正し、`レビュー状態 = 確定` にする（詳細は [`../docs/operations/review-workflow.md`](../docs/operations/review-workflow.md)）

### Human-in-the-Point ルール
- AI autofill は「下書き」扱い
- 確定は必ず人手レビュー後
- レビュー前のinsightは集計・戦略立案に使用しない
- 確定済みinsightのみ VPC / BMC 連携対象とする

### 見直しトリガー
- 20〜30件たまった時点で `顧客属性` 分類を見直す
- 50件たまった時点で `Forces` ラベルの判定精度を検証
- AI autofill のハルシネーション率が10%超なら、プロンプトを再設計

## 移行手順（v1.3 → v2.0）

### Step 1: 既存データバックアップ
- v1.3のDBを複製してアーカイブ保管

### Step 2: 新プロパティ追加
- `Forces` `役職・立場` `所属部門` を追加

### Step 3: AI autofill で `要約` 一括生成
- 既存データの `生の声` を入力に、新フォーマットで `要約` を再生成
- 同時に `Forces` を自動付与

### Step 4: 人手レビュー
- 既存データの `Forces` 妥当性を全件確認

### Step 5: 旧プロパティ削除
- `困りごと` `望む結果` `不安` `変化の動機` `選定基準` `見送り理由` を削除
- 削除前に `タグ` への移管が必要なものを移管（特に `選定基準` `見送り理由`）

## モデル使い分け方針

| 用途 | モデル | 理由 |
|---|---|---|
| Notion AI autofill | **Opus 4.6** | 構造化出力の精度が高く、Forces判定のニュアンスを捉えやすい |
| 一般的なテキスト処理・要約検証 | **Sonnet 4.6** | コスト効率と速度のバランスが良い |
| 戦略立案・VPC/BMC変換 | **Opus 4.6** | 複雑な推論が必要 |
| insight DBの定期メンテナンス | **Sonnet 4.6** | 定型処理 |

---

## Forbidden Actions

⚠️ AI autofill の出力を人手レビューなしに確定しない
⚠️ `生の声` に明示されていない情報を AI に推測させない
⚠️ `重要度` `確からしさ` を AI に判定させない（必ず人手）
⚠️ 旧プロパティの削除を Step 4 完了前に実施しない
⚠️ 移行作業中の本番運用は停止する
